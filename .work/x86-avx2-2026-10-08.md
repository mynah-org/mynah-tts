# PocketTTS on x86 AVX2 without AVX-512 or VNNI -- AMD EPYC 7702, 2026-10-08

First Pocket numbers for the cheap x86 server class: AVX2 + FMA + F16C, no
AVX-512, no VNNI (Zen 2 / Zen 3 EPYC, pre-Ice-Lake Xeon). Branch
`perf-x86-avx2`. Everything below was measured on one rented box in one day;
every change is byte-identical in audio (sha256) and lands as the default.

**In one paragraph.** On a 24.6-CPU slice of an EPYC 7702 the 24-layer pack
went from single-request RTF 0.435 to 0.311 at two threads (-28%) and from a
streaming-server knee of C12 to C24 (2-minute screens, 6 x 4 workers;
15.1 -> 22.6-23.3 audio-s/s); the 6-layer pack from RTF 0.286 to 0.210 (-27%)
and from a knee of C28-C36 to C36-C42 (+25-28% audio-s/s at equal load), or
C56 with an int8 backbone that changes the audio and is reported, not
defaulted. The work was an exact AVX2 int8 dot (VPSIGNB + VPMADDUBSW) with a
DRAM-friendly row walk, a 6x16 sgemm tile, memoised codec weight layouts,
register-resident attention, a faster bf16 single-activation kernel and a
cgroup-aware default pool size. Against the Axion points this slice delivers
a quarter (24L) to a third (6L) of an Axion core's streaming capacity per CPU.

## Where x86 fell behind the Axion path

Per-stage, CLI, 2 threads (the serving worker width), same text and seed,
`--batch B`, ms per step (backbone) or per slot-frame (codec):

| stage (24L) | x86 base B1 | B4 | B8 | per-slot slope | Axion 24L slope (09-26, 2 thr) |
|---|---|---|---|---|---|
| step.backbone | 18.1 | 52.3 | 87.7 | **9.9 ms/slot** | 5.6 ms/slot |
| codec.transformer / frame | 4.32 | 4.27 | 4.16 | flat | 2.5 |
| codec.conv_stack / frame | 6.18 | 6.30 | 5.94 | flat | 2.5 |
| flow.head / step | 1.04 | 1.75 | 2.62 | | 0.7-1.75 |

Per slot-frame at B4: 13.1 + 4.3 + 6.3 = ~24 ms on x86 against ~13 ms on
Axion. The codec does not batch, so it is a per-slot cost at every width.

Kernel by kernel, against the ARM path:

| stage | ARM (Neoverse-V2) | x86 AVX2 before | finding |
|---|---|---|---|
| int8 backbone / codec tf linears | SDOT quad + I8MM x4/x6/x8 tiles | `dot_q8_i32_avx2`: 2 loads + 2 widening shuffles per 16 MACs, activation re-widened per row, horizontal sum per row; **batched path fell through to one weight pass per activation** (the x86 weight-stationary arm is gated on the VNNI u8 encoding) | the main gap |
| codec conv taps | int8 SDOT (convq8) | f32 sgemm 4x16 tile (8 accumulators, below the FMA-latency need); fused tap region **re-gathers the whole weight with a `kernel` stride every frame**; convtranspose walks W^T in place, a 12 KiB column stride | layout + tile |
| attention (backbone, codec tf) | pooled; NEON dot | one `mynah_dot_f32` per key (serial 8-FMA chain + hsum + call), one `mynah_axpy_f32` per key (load+store of the head row per key) | latency-bound |
| bf16 backbone (6L) | tiled BFMMLA | shift-widen to f32 (no AVX512-BF16) | not touched, see next steps |
| act. quantizer | NEON vcvta | scalar source, but gcc auto-vectorises it (checked in the disassembly) | fine |
| softmax | scalar `expf` | scalar `expf` | not touched (numerics) |
| GELU / Snake / ELU | NEON | AVX2 (exists) | fine |
| pool size | 2 per worker | CLI/library default 64 threads on a 24.6-CPU quota | fixed |

int8 codec conv on AVX2 was measured rather than assumed (`MYNAH_CODEC_CONV_Q8=1`,
existing flag, changes the audio): the conv stack went 590 -> 551 ms while the
f32 path after the layout fix below is 490 -> 438 ms. On Zen 2 VPMADDUBSW and
VPMADDWD share one multiplier pipe, so an int8 dot without VNNI peaks at the
same 16 MAC/cycle as two f32 FMA pipes, and quantizing the window costs 10%.
**The host gate is right; it stays off.**

### 6L with an int8 backbone -- a numerics change, NOT a default

### Where a worker's time goes under load (MYNAH_SERVE_PROFILE + MYNAH_COST_MAP=2)

24L, final, 11 x 2 at C20 (mean 1.9 live slots per worker): loop = step
88-90%, prefill-first 5-7%, prefill-cont 1.4-2.7%, other ~1%. Step cost
**B1 32-39 ms, B2 52-61 ms**. Per worker: `step.backbone` 36.7 ms per step,
`codec.transformer` 2.83 ms and `codec.conv_stack` 4.99 ms per slot-frame,
`flow.head` 2.4 ms per step.

The backbone under load runs **~1.8x slower than the same step in the
isolated CLI** (B2 there: ~20 ms), while the codec runs ~1.2x slower. Eleven
workers each stream the 302 MB int8 backbone once per step -- ~60 GB/s of
weight traffic in aggregate, on a socket whose DRAM and L3 are shared with
other tenants of the host. That is why fewer, wider workers win for the 24L
(6 x 4 reads the weights 6 times per frame period instead of 11) and why the
int8 kernel's DRAM shape (one sequential row stream per thread) mattered more
than its arithmetic.

6L, final, 11 x 2 at C36 (mean 2.9 live): step 85-87%, prefill-first 8.5-9%,
prefill-cont 3-5%. Per worker: `codec.conv_stack` 4.7 ms + `codec.transformer`
2.8 ms per slot-frame = **49% of the wall**, `step.backbone` (bf16) 19 ms per
step = 33%, prefill projections 12%. **For the 6-layer pack the codec is the
dominant kernel under load**, and it is decoded per slot with no batching
across slots.

### Against the Axion points (different machine, different core count)

| | GCP Axion c4a-32 (Neoverse-V2, 32 cores, no SMT) | EPYC 7702 slice (24.6-CPU quota) |

| 24L | C88 GOOD, 30-min soak, 121.4 audio-s/s (16 x 2) | knee C24 on a 2-minute screen, 23.3 audio-s/s (6 x 4) |
| 6L | C164 GOOD, 30-min soak, 193.3 audio-s/s (16 x 2, mb 12) | knee C36-C42 on 2-minute screens, 42-45 audio-s/s (11 x 2); C56 with an int8 backbone |

So the cheap AVX2 slice sustains roughly a quarter (24L) to a third (6L) of
an Axion core's streaming capacity per CPU. The reasons are not hidden: SDOT
and I8MM / BFMMLA against an exact AVX2 emulation (16 MAC/cycle on one Zen 2
multiplier pipe), 2019 Zen 2 cores sharing DRAM with other tenants, and a
quota CPU that is a scheduler share, not a dedicated core. Neither x86 number
is a qualified operating point; both are screens.

## What to try next

1. **The 6L backbone on AVX2: int8, or a better bf16 batch kernel.** The 6L
   backbone is bf16, and this branch only fixed its single-activation kernel
   (four rows per pass, `2ede25a`); the four-activation kernel that serving
   runs is unchanged (a two-row version lost 7%). The bigger lever is int8:
   2.4x faster per step and the 6L serving knee moves from C42 to C56 (see
   the serving section); it needs a quality gate before it can be a default.
2. **The codec is the dominant kernel under load for the 6L** (49% of a
   worker's wall at C36: conv stack 4.7 ms + transformer 2.8 ms per
   slot-frame) and a third of the 24L's, and it is decoded per slot with no
   batching across slots. A cross-slot codec tile (one GEMM over the B slots'
   frames: n = 16*B instead of 16, every codec weight read once per step
   instead of once per slot) is the next lever on both packs. The SEANet
   serial phases (window copy, convtranspose scatter, copies: ~16% of the
   conv stack) are the smaller one.
3. **Weight traffic under load (24L).** The int8 backbone step runs ~1.8x
   slower inside an 11-worker server than alone; fewer, wider workers (6 x 4)
   already won one knee level. A topology sweep at the knee (5 x 5, 6 x 4,
   8 x 3 with larger max-batch) and a shared-weights check of DRAM bandwidth
   per worker are cheap next steps.
4. **Softmax `expf`** is scalar libm on every target; a vector exp changes the
   numerics and needs the usual quality gate rather than a sha.
5. **Single request at high thread counts** barely moved (-4..-7% at 24
   threads): the per-op pool barrier dominates, as on Axion.
6. **Qualification.** Every serving number here is a 2-3 minute screen on a
   shared host; the knees need 30-minute soaks (and a quiet host, or a second
   host for the load generator) before they become operating points.

What VNNI / AVX-512 hosts add (none measured here):

- **AVX-VNNI / AVX512-VNNI** (Zen 4/5, Ice Lake+, Alder Lake+): VPDPBUSD does
  the int8 multiply-add in one instruction on the u8 encoding; the existing
  `dot4_u8_vex/evex` kernels resolve automatically and take precedence over
  this branch's sign trick. The weight-stationary u8 batched arm already
  exists for them.
- **AVX-512BW without VNNI** (Skylake-SP, Cascade Lake): these hosts stay on
  the signed encoding, so they now get this branch's AVX2 sign-trick kernels
  for the row walks and batches (exact, so no numerics change), with the
  existing `dot_q8_i32_avx512bw` left on the one-row tails. A 512-bit twin of
  the sign trick (`_mm512_maddubs_epi16`) would double the width -- not
  written, and not measurable on this box.
- **AVX512-BF16** (Cooper Lake, Sapphire Rapids, Zen 4+): VDPBF16PS for the
  6L bf16 backbone, already resolved by `matvec_bf16_dpbf16_*`.
- Note: Zen 3 has **no** AVX-512; it is an AVX2 host like this one.
