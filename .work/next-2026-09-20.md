## The open lever, and it is no longer the prefill

At C130, TTFB triples (74.8 -> 200.7 ms) because **16 workers x 8 slots is 128
places and 130 requests is the first level that fills them**. Requests wait for a
slot before synthesis begins. Three things follow:

* `--max-batch` is a live knob again. This morning it measured as inert because
  the loop never reached 7 live slots; at C120 the width histogram reaches **B7
  with 92015 frames and B8 with 62154**. That finding expired the day it was made.
* The choices are more slots per worker (`--max-batch` up), more workers, or
  admission that does not make a request wait for a slot to synthesise its first
  token.
* Nothing here is prefill any more. Every prefill lever is spent: the cap is
  measured, the order is FIFO, the kernel is BFMMLA.

## Two claims that expired the same day they were written

Kept rather than deleted, because a reader who finds the old line should find the
correction beside it.

**"cap = deadline - T_frame(B typical)" is not a law.** It produced 30 ms for the
f16 kernel and was right then. `T_frame(B)` with bf16 is **2.9 + 6.8*B** (f16:
3.0 + 7.8*B), so at the modal width B7 the slack reads 28 ms and the rule says
LOWER the cap — while 40 beats 30 by sixty milliseconds of TTFA. A frame that
overruns is a **debt, not a stall**: at RTF 0.79 a slot earns 16 ms of lead per
frame and repays ten inside one.

**"`--max-batch` is not an active knob"** — see above.

## The lesson worth carrying, if only one survives

The tiled BFMMLA kernel is **14.68x** on the isolated GEMM and bought fourteen
points of concurrency. **FIFO touches no multiply at all** — it changes only the
order in which waiting prefills are served — and took more off TTFA than the cap
did. Round-robin looked like the neutral, fair choice; it is the policy that
makes everyone finish when the last one would.

And the decision was only defensible because the instrument was extended first:
`tools/serving_profile.py` reported the class MIX but never per-class latency, so
an aggregate p95 could not distinguish a real win from long texts finishing by
making short ones wait. Per-class TTFA was added BEFORE the call, and it said the
suspicion was wrong — short -30%, medium -25%, long -22%, nobody pays.

## Smaller things left on the floor

* **`Retry-After` on the 503.** Fail-fast admission is correct and verified
  (`job_enqueue` refuses at `pending >= max_pending` under the mutex and answers
  503 with `rejected++` before any synthesis, `server/main.c:376,1208`), and
  `/health` publishes `queued`/`rejected`/`queue_capacity`. The 503 carries no
  `Retry-After`, so every client invents its own backoff. One line.
* **AVX512-BF16 (`VDPBF16PS`)** is unwritten and the trap is recorded next to
  where it goes: it multiplies pairwise within a lane and `_mm512_cvtne2ps_pbh`
  interleaves its sources, so the converted activation does not land k-adjacent
  without care. It needs a machine with the unit, which this project has none of.
* **The client PDF and the sample bundle** on the Desktop describe C110 and the
  f16 backbone. Both are superseded by C120 and bf16 and should be regenerated
  before being sent anywhere. `reports/20260919-c96-axion/client_report.py`.
* **`codec_*:bf16`** was never tried. The codec is not autoregressive, so a
  rounding error there is additive noise measurable against f32 exactly as int8's
  was — and int8, far coarser, was accepted there. No code needed:
  `MYNAH_QUANT_GROUPS=codec_transformer:bf16` works today.
